# Arquitectura de Forja

Forja se organiza como un workspace Rust de 7 crates con dependencias acíclicas y fronteras estrictas. Ningún crate de bajo nivel conoce el planificador, el servidor HTTP ni la interfaz de línea de comandos.

## Crates y fronteras

### `forja-core`
Define el lenguaje común del dominio: `Task`, `Privacy`, `AgentKind`, `RunStatus`, `RunRecord`, `ForjaError` (con `thiserror`) y la política de privacidad (`allowed_agents`, `is_agent_allowed`, `check_policy`). No realiza operaciones de E/S, red ni procesos; su frontera es puramente de tipos, serialización (`serde`) y reglas de negocio puras, de modo que el resto de crates dependen de él sin ciclos.

### `forja-git`
Encapsula la interacción con el binario `git` del sistema mediante `std::process::Command` para crear worktrees aislados (`create_worktree`), consultar la rama activa (`current_branch`), verificar el estado limpio (`status_clean`) y registrar commits locales (`commit_all`). Cierra el ciclo de revisión con `diff_worktree` (cambios frente a la rama base), `merge_branch` (exige rama base y árbol limpio, y anula la fusión si hay conflicto), `remove_worktree` y `delete_branch` (idempotentes). Depende únicamente de `forja-core`. Por diseño de seguridad, no existe ninguna función ni invocación de `push` en este crate.

### `forja-agent`
Define el contrato asíncrono `Agent` (object-safe vía `Pin<Box<dyn Future>>` para soportar `Arc<dyn Agent>` sin macros externas), `RunContext`, `AgentOutput`, la implementación determinista `MockAgent` y el ejecutor común `Runner` (`tokio::process::Command` sin shell, con timeout, captura y streaming de salida). Sobre él viven seis adaptadores funcionales que construyen su argv con funciones puras (`build_command`) y parsean la salida de forma tolerante: `AgyAgent` (`agy`, con `parse_agy_output`), `ClaudeAgent` (`claude -p` con `--output-format json`, `--permission-mode acceptEdits` y `--effort` opcional), `OpencodeAgent` (`opencode run --model … --auto --title forja`, con el esfuerzo como variante `#nivel` del modelo y un reintento sin variante si el modelo no la admite), `HermesAgent` (`hermes -p <perfil> chat --query-file <temporal> -Q --oneshot`, con perfiles descubiertos y ocultables, `-m` y `--reasoning` opcionales y limpieza garantizada del archivo temporal), y `LocalAgent` (invoca `opencode run` contra el servidor OpenAI-compatible de `llm` en el puerto 8081, resuelve los alias `moe`/`flash` y falla sin arrancar nada si el puerto no escucha). Solo devuelven `ForjaError::NotConfigured` cuando el binario o servicio correspondiente no está disponible. Depende solo de `forja-core`; nunca conoce repositorios git, políticas de cola ni almacenamiento.

### `forja-store`
Provee persistencia local append-only en formato JSONL (`JsonlStore` sobre `runs.jsonl` en un directorio configurable) con `append_run`, `list_runs` y `get_run`. Al leer, reconstruye el último estado de cada `run.id` en orden estable y tolera líneas vacías o JSON corrupto sin producir `panic`. Depende exclusivamente de `forja-core`.

### `forja-sched`
Orquesta el ciclo de vida completo de cada ejecución en `Scheduler`: valida primero la política de privacidad (`check_policy`) antes de persistir o crear worktrees, limita la concurrencia simultánea mediante `tokio::sync::Semaphore` (por defecto `2`), prepara worktrees y commits opcionales con `forja-git`, reintenta fallos con backoff configurable (hasta `2` reintentos por defecto), permite cancelación (`cancel_run`) y persiste cada transición de estado en `forja-store`. Depende de `forja-core`, `forja-git`, `forja-agent` y `forja-store`.

### `forja-server`
Expone `Scheduler` sobre HTTP con `axum`: API REST (`POST /tasks`, `GET /runs`, `GET /runs/{id}`, `POST /runs/{id}/cancel`, `GET /runs/{id}/diff`, `POST /runs/{id}/merge`, `POST /runs/{id}/discard`) y un panel web local autocontenido (`GET /`, embebido con `include_str!("panel.html")`, sin CDN ni recursos externos). Mapea errores de dominio a códigos HTTP adecuados (`403` para `PolicyDenied`, `404` para `NotFound`, `400` para entradas/agentes no configurados, `409` para conflictos de revisión como una ejecución activa, un worktree ya cerrado o un merge con conflictos). El módulo `review` concentra diff, fusión y descarte; serializa esas operaciones y solo acepta ramas `forja/<id>` con worktrees dentro de la carpeta configurada. El módulo `reactor` escucha el `broadcast` del planificador y registra las ejecuciones delegadas (bloques `[[forja:delegar]]` o `?conversation_id=` de Hermes); al terminar, da un turno automático al orquestador con el resultado resumido, agrupa los avisos de una conversación, espera si el usuario está hablando y limita a `MAX_AUTO_TURNS` los turnos automáticos seguidos para evitar bucles. Depende de `forja-core`, `forja-agent`, `forja-git`, `forja-store` y `forja-sched`.

### `forja-cli`
Binario `forja` construido con `clap` que ensambla la configuración local (`--store-dir`, `--worktrees-dir`, `--repo`, `--base-branch`) y ofrece los subcomandos `run`, `list` y `serve`. Es el único crate ejecutable del workspace y el punto de entrada que conecta `forja-store`, `forja-sched`, `forja-agent` y `forja-server`; también aloja las pruebas de integración de extremo a extremo (`tests/e2e.rs`).
